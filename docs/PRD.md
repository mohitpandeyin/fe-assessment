# Product Requirements Document: Markdown File Preview and Rich Copy

**Version:** 1.0  
**Date:** 2026-08-12  
**Status:** Draft for validation - implementation not started  
**Owner:** Project author

## 1. Purpose of this document

This PRD converts the supplied frontend assignment into a complete, testable product definition. It establishes what must be built before implementation planning begins.

The original assignment remains authoritative. This document separates:

- **Required:** explicitly mandated or necessary to satisfy an explicit mandate.
- **Derived:** necessary for a complete and dependable user experience, even when the assignment does not state the behavior word-for-word.
- **Optional:** useful only after all required and derived behavior is complete.
- **Out of scope:** intentionally excluded from the first release.

## 2. Product summary

A local-first web application that lets a user upload a Markdown document, view an accurate and polished rendered preview, and copy that rendered document once for pasting into rich-text or plain-text destinations.

The application processes one document at a time and runs entirely in the browser. It is optimized for Markdown generated by AI models, which may be long, structurally complex, or partially malformed.

## 3. Product vision

Make an unfamiliar Markdown file immediately readable and portable without requiring the user to understand Markdown syntax, install a desktop tool, or manually reformat content after pasting it elsewhere.

The experience should feel like opening a clean document viewer: fast, calm, dependable, and focused on the content.

## 4. Objectives

### 4.1 Primary objectives

1. Render the required GitHub-Flavored Markdown constructs accurately and consistently.
2. Turn a local file into a polished reading experience with minimal user effort.
3. Preserve useful formatting when the rendered document is copied into Word, Google Docs, and rich-text editors.
4. Provide readable plain text when the destination or browser cannot accept rich content.
5. Remain usable when input is unexpected, incomplete, empty, or malformed.
6. Demonstrate strong frontend engineering, visual design, responsiveness, accessibility, and project organization.

### 4.2 Prioritization aligned with evaluation

The assignment weights the work as follows:

| Area | Weight | Product implication |
|---|---:|---|
| UI/UX and visual quality | 35% | The upload, reading, feedback, and recovery experiences must feel finished. |
| Markdown rendering accuracy | 25% | Required syntax and reasonable edge cases need direct verification. |
| Code quality and organization | 20% | Responsibilities and state should be clear and testable. |
| Responsiveness and accessibility | 15% | Essential workflows must work across screen sizes and input methods. |
| Thoughtful enhancements | 5% | Enhancements follow the polished core and must not jeopardize it. |

## 5. Core problems

### 5.1 Markdown is not universally readable

Raw Markdown exposes syntax that can distract non-technical readers and obscures the intended document hierarchy.

### 5.2 Complex or AI-generated Markdown is inconsistent

AI output may combine deeply nested lists, wide tables, multiple code languages, unfinished fences, unusual spacing, or unsupported extensions. A fragile renderer can produce confusing output or crash.

### 5.3 Copying from a preview often loses formatting

Copying only source Markdown is not useful to a rich-text destination. Copying DOM content that depends on application CSS can also lose typography, borders, spacing, and code formatting when pasted.

### 5.4 Browser clipboard capabilities vary

Not every browser accepts arbitrary clipboard MIME types. The product must provide the richest available representation without making Copy unreliable.

### 5.5 File viewers often provide weak feedback

Users need clear confirmation of which file is open, whether it was read successfully, what Copy did, and how to recover from an invalid or unreadable file.

## 6. Target users and use cases

### 6.1 Primary user

A person who has a local Markdown document and wants to read or transfer it without installing or configuring a Markdown tool.

Typical use cases:

- Preview an AI-generated technical document.
- Inspect a README, proposal, report, or notes file.
- Copy a formatted document into Word, Google Docs, email, or another rich-text editor.
- Copy a readable plain-text version into a text-only destination.

### 6.2 Evaluation user

An assessor who uploads known and hidden Markdown files to verify syntax support, resilience, presentation quality, accessibility, and clipboard behavior.

## 7. Roles and permissions

The first release has no accounts, authentication, authorization service, or persistent roles.

| Role | Permissions | Restrictions |
|---|---|---|
| Local user | Select/drop a local Markdown file, view it, copy rendered content, replace it, and remove it from the current session. | Cannot edit the source in the application, upload more than one active file, or save content to a server. |
| Evaluator | Same product permissions as a local user; may exercise hidden inputs and browser/device combinations. | Has no privileged admin controls. |
| Application | Read only the file explicitly supplied by the user and request clipboard write access only after the user invokes Copy. | Must not inspect unrelated local files, execute uploaded scripts, or transmit document contents. |

## 8. Scope

### 8.1 In scope for v1

- One-file local upload and drag-and-drop.
- Accurate rendering of the required Markdown constructs.
- A polished responsive document preview.
- Clear file, empty, error, and clipboard feedback states.
- A single multi-representation Copy action.
- Safe browser-only processing.
- Accessibility for the complete core workflow.
- Documentation and tests sufficient to explain and verify the solution.

### 8.2 Out of scope for v1

- Markdown authoring or a live source editor.
- Saving modifications to the uploaded file.
- Multiple open files, tabs, folders, or workspaces.
- Accounts, roles administration, synchronization, collaboration, or sharing.
- Backend services, databases, analytics, or document-content uploads.
- Version history, comments, review workflows, or publishing.
- PDF/DOCX export and print-specific authoring controls.
- Guaranteed rendering parity with every Markdown dialect.
- Repairing every malformed document.

## 9. Information architecture and product states

The application has one primary page and four meaningful states.

### 9.1 Empty state

- Briefly explains the product's purpose.
- Offers one clear file-selection action and a drag-and-drop target.
- Communicates accepted file expectations and local-only processing.
- Does not show inactive document actions as though content exists.

### 9.2 Loading state

- Indicates that the selected file is being read or prepared.
- Prevents duplicate actions while the same operation is pending.
- Remains visually stable for fast files; no disruptive full-screen transition is required.

### 9.3 Document state

- Displays the active filename and useful lightweight metadata where reliably available.
- Provides the single document-level Copy action.
- Provides clear Replace and Remove/New document actions without competing with Copy.
- Renders content in a constrained, readable document surface.

### 9.4 Recoverable error state

- Describes what failed in plain language.
- Preserves the previously valid document if a replacement file fails to read.
- Offers a direct retry or file-selection path.
- Never leaves the user with a blank screen or an uncaught application failure.

## 10. Functional requirements

Requirement IDs are stable references for planning and testing.

### 10.1 File intake

#### FR-001 - Select one local Markdown file [Required]

The user can invoke the browser file picker and select one file. The interface should prefer `.md` and `.markdown` files while recognizing that browser MIME metadata may be missing or inconsistent.

**Acceptance criteria**

- Only one file becomes active.
- A successfully read replacement supersedes the previous file.
- Cancelling the picker does not change the current state.
- The browser does not upload the file to a server.

#### FR-002 - Drag and drop [Derived]

The primary upload surface accepts a dropped file as an equivalent input method.

**Acceptance criteria**

- The drop target visibly responds while a file is dragged over it.
- Dropping no files or multiple files produces clear, recoverable feedback.
- If multiple files are dropped, the app does not silently merge them. It asks the user to provide one file or deterministically accepts only one while clearly stating the result.

#### FR-003 - Validate input without over-relying on MIME type [Derived]

The app validates that the input is a readable text-like Markdown file. File extension and MIME type can inform feedback but cannot be the only check because Markdown MIME reporting varies by platform.

**Acceptance criteria**

- Unreadable and clearly non-text inputs produce a helpful error.
- Empty files are handled as valid but empty documents, with a clear empty-document message.
- Validation failure does not crash the application.
- A failed replacement does not destroy an already valid preview.

#### FR-004 - Replace and remove the document [Derived]

The user can select another file or clear the current document.

**Acceptance criteria**

- Replace reuses the same one-file intake behavior.
- Remove clears source content, derived render data, filename, and transient copy status from application memory.
- The app returns to the empty state after removal.

### 10.2 Markdown rendering

#### FR-010 - Render required block elements [Required]

The preview correctly renders:

- Headings.
- Paragraphs.
- Ordered lists.
- Unordered lists.
- Nested lists.
- Tables.
- Blockquotes.
- Fenced and indented code blocks where produced by the baseline parser.

**Acceptance criteria**

- Heading levels are visually distinct and retain semantic `h1`-`h6` structure.
- Ordered and unordered list markers remain distinguishable at nested depths.
- Wide tables remain usable without forcing the entire page wider than the viewport.
- Code preserves whitespace and can be horizontally scrolled when necessary.
- Blockquotes are distinct without reducing text contrast below the accessibility target.

#### FR-011 - Render required inline elements [Required]

The preview correctly renders:

- Inline code.
- Bold text.
- Italic text.
- Strikethrough text.
- Hyperlinks.

**Acceptance criteria**

- Inline formatting can be combined without exposing syntax markers incorrectly.
- Inline code is distinguishable from prose and does not introduce unintended line breaks.
- Links are visually identifiable, keyboard reachable, and preserve their intended URL.
- Unsafe URL schemes are rejected or rendered inert.

#### FR-012 - Follow GFM as the baseline [Required]

The selected parser and configuration follow GitHub-Flavored Markdown for required constructs, including GFM table behavior and strikethrough.

Task lists and autolinks should be supported because they are standard GFM behavior and appear in representative input, but they remain secondary to the assignment's explicit list.

#### FR-013 - Handle malformed or incomplete Markdown [Required]

The renderer must tolerate reasonable malformed input and incomplete constructs.

**Acceptance criteria**

- An unclosed emphasis marker, link, list, blockquote, table row, or code fence does not trigger an uncaught error.
- Content the parser cannot interpret remains readable as literal or best-effort text.
- One malformed region does not prevent unrelated document sections from rendering when the parser can recover.
- If rendering itself fails, the user sees a recoverable error and can choose another file.

#### FR-014 - Handle representative optional syntax safely [Derived]

Unsupported syntax such as definition lists, math delimiters, and admonition markers must degrade to readable content rather than disappear or execute code.

HTML comments may remain invisible according to normal Markdown/HTML behavior. Raw embedded HTML is not required and must never enable script execution.

#### FR-015 - Resolve document links safely [Derived]

- External `http` and `https` links may open in a new browser context with appropriate `noopener`/`noreferrer` protection.
- Same-document heading anchors should work when generated.
- Local relative links and images cannot be assumed to resolve because only one file is granted to the browser. They must fail gracefully rather than create unsafe file access.

### 10.3 Reading experience

#### FR-020 - Present a polished document surface [Required]

The rendered output uses deliberate typography, hierarchy, spacing, contrast, and content width appropriate for long-form reading.

**Acceptance criteria**

- Normal prose remains readable on narrow and wide screens.
- Long URLs, inline code, and unbroken strings wrap or scroll without breaking the layout.
- Tables and code blocks have deliberate overflow behavior.
- Content is not visually confused with application navigation or file controls.
- Layout and typography remain consistent across every required element.

#### FR-021 - Communicate active file context [Derived]

The document state identifies the active file and makes it clear that the displayed content came from that local file.

#### FR-022 - Preserve application stability for long documents [Derived]

The app must remain interactive for reasonably sized technical documents. Exact maximum file size is a planning decision; the UI must provide a clear warning or rejection rather than freeze indefinitely for a file beyond the supported limit.

### 10.4 Clipboard export

#### FR-030 - Provide one primary Copy action [Required]

The document state contains a single Copy button that copies the complete rendered document, not the application chrome and not just a selected block.

#### FR-031 - Write multiple clipboard representations [Required]

On Copy, the application attempts one clipboard item containing:

- `text/html`: semantic rendered HTML.
- `text/plain`: readable plain text derived from rendered content.
- `text/markdown`: the exact original Markdown source where the browser permits it.

The destination application chooses the richest format it supports.

**Acceptance criteria**

- Rich-text destinations receive headings, paragraphs, emphasis, lists, tables, blockquotes, links, and code with useful structure.
- Plain-text destinations receive readable content rather than HTML markup.
- The Markdown representation preserves the original source exactly; it is not regenerated from HTML.
- Only the document content is copied—filename controls, Copy buttons, notifications, and other interface elements are excluded.

#### FR-032 - Produce portable clipboard HTML [Required]

Copied HTML must preserve useful formatting outside the application.

**Acceptance criteria**

- The export uses semantic HTML.
- Essential presentation is expressed in portable inline styles or equivalent self-contained markup.
- Export correctness does not depend solely on Tailwind classes, CSS variables, an external stylesheet, or JavaScript.
- Unsafe elements, event handlers, scripts, and application-only attributes are absent.
- Paste behavior is manually verified in at least one rich-text destination and one plain-text destination before release.

#### FR-033 - Degrade clipboard behavior gracefully [Derived]

Clipboard support is capability-based.

**Acceptance criteria**

- Unsupported `text/markdown` does not prevent HTML and plain text from being copied.
- If multi-format `ClipboardItem` writing is unavailable or rejected, the app attempts a plain-text clipboard fallback.
- A failed browser permission or clipboard operation produces actionable feedback without losing the document.
- Copy is initiated only by a user gesture.

#### FR-034 - Confirm Copy outcome [Derived]

The interface communicates success or failure accessibly. Feedback must not rely only on color and must not permanently change the button's meaning.

### 10.5 Privacy and safety

#### FR-040 - Keep processing local [Required]

The application reads and processes document content entirely in the browser. It does not send the source or rendered output to a backend or third party.

#### FR-041 - Treat Markdown as untrusted input [Derived]

- Script execution and inline event handlers are prohibited.
- Dangerous link schemes are blocked.
- Raw HTML, if ever supported, must pass through an explicit allowlist-based sanitizer.
- A Content Security Policy should be considered at deployment even when the React renderer is safe by default.

## 11. User flows

### 11.1 First-time upload and preview

1. User opens the application.
2. User reads the concise purpose statement and local-processing assurance.
3. User selects or drops one Markdown file.
4. Application validates and reads the file locally.
5. Application renders the document.
6. User reads the preview and can copy, replace, or remove the file.

**Failure branch:** If the file cannot be read or is clearly invalid, the application explains the problem and keeps the user in a usable upload state.

### 11.2 Replace an existing document

1. User invokes Replace or drops another file.
2. Application reads the candidate file without immediately destroying the active document.
3. On success, the candidate becomes active and the preview moves to the new document's starting position.
4. On failure, the current document remains active and recoverable feedback is shown.

### 11.3 Copy to a rich-text destination

1. User invokes Copy.
2. Application prepares safe portable HTML, readable plain text, and supported original-Markdown data.
3. Application writes one clipboard item using supported representations.
4. Application announces success.
5. The destination selects `text/html` and retains useful document formatting.

### 11.4 Copy fallback

1. User invokes Copy in a browser without usable multi-format clipboard support.
2. The rich write is unavailable or rejected.
3. Application copies the readable plain-text representation when possible.
4. Application tells the user that plain text was copied, or provides an actionable failure message if no write succeeds.

### 11.5 Remove and reset

1. User invokes Remove/New document.
2. Application clears document-related in-memory state.
3. Application returns focus to an appropriate location in the empty state.

## 12. UX and interaction requirements

### 12.1 Visual principles

- Document-first: controls support the content rather than dominate it.
- Calm and professional: avoid novelty UI that competes with reading.
- Clear hierarchy: application frame, file context, document title, sections, and metadata are distinguishable.
- Consistent rhythm: Markdown elements use a coherent spacing and typography system.
- Purposeful motion only: animation is optional and must respect reduced-motion preferences.
- The approved Direction C visual system uses a dark graphite header, neutral document workspace, compact controls, restrained teal feedback, and minimal shadow. Detailed rules live in the [UI specification](./UI_SPECIFICATION.md) and [design system](./DESIGN_SYSTEM.md).
- In the loaded desktop state, a contextual sidebar shows real uploaded-file details and a **Start over** action. It does not show a table of contents in v1.

### 12.2 Feedback principles

- Every asynchronous or permission-sensitive action has visible status.
- Errors explain recovery rather than exposing technical stack details.
- Success messages are brief and do not obstruct reading.
- Drag/drop, focus, hover, disabled, loading, success, and error states are visibly distinct.

### 12.3 Responsive behavior

- Mobile: actions remain reachable, document padding is reduced appropriately, wide content scrolls within its own region, and the desktop file-details sidebar becomes an on-demand sheet or disclosure.
- Tablet: controls and document metadata adapt without crowding the content.
- Desktop: content width remains comfortable rather than stretching prose across the full viewport; the loaded layout includes a narrow file-details sidebar beside the document workspace.

## 13. Accessibility requirements

Target WCAG 2.1 AA for the core workflow.

- All actions work with keyboard alone.
- File input has an accessible name and is not represented only by an unlabeled drop area.
- Drop behavior has a file-picker equivalent.
- Focus order follows the visual workflow.
- Focus indicators are clearly visible.
- Text and meaningful UI indicators meet appropriate contrast ratios.
- Heading semantics preserve document structure.
- Tables retain semantic headers where produced by Markdown.
- Links are identifiable without color alone.
- Status and error feedback is announced using an appropriate live region.
- Icon-only controls, if any, have accessible names and adequate hit targets.
- Motion respects `prefers-reduced-motion`.
- Browser zoom and narrow widths do not hide essential functionality.

## 14. Technical considerations and constraints

This section guides planning but does not authorize implementation yet.

### 14.1 Mandatory platform choices

- React.js.
- JavaScript only; no TypeScript source.
- Tailwind CSS for application and preview styling.
- Client-side execution only.
- Any React-compatible framework is allowed; no framework-specific feature is currently required.

### 14.2 Rendering architecture

A suitable renderer must:

- Follow CommonMark/GFM semantics for the required constructs.
- Support custom renderers/components for consistent styling and safe link behavior.
- Avoid executing raw HTML by default.
- Tolerate malformed input.
- Expose enough structure to create a portable clipboard representation.

`react-markdown` with `remark-gfm` is the current recommended candidate because it produces React elements and supports a plugin pipeline. `markdown-it` is also capable and is the parser used by VS Code's built-in preview, but it produces HTML and therefore requires a deliberate sanitization/injection strategy in React. Final selection belongs in technical planning.

### 14.3 Separation of concerns

Planning should preserve clear boundaries among:

- File validation and reading.
- Document/application state.
- Markdown parsing and onscreen rendering.
- Clipboard HTML/plain-text serialization.
- Clipboard capability detection and writing.
- User feedback and accessibility announcements.

### 14.4 Clipboard considerations

- The Async Clipboard API generally requires HTTPS or localhost and a user gesture.
- MIME support must be detected or attempted defensively.
- `text/markdown` support is not universal.
- Clipboard HTML requires a dedicated portability review; onscreen Tailwind styling alone is insufficient.
- Permission denials and browser policy restrictions are expected runtime conditions, not fatal application errors.

### 14.5 File considerations

- `File.text()` or an equivalent browser API can read the supplied file.
- MIME type can be empty for Markdown and must not be treated as definitive.
- UTF-8 should be the expected encoding; invalid or unusual encoding must fail gracefully.
- Size limits and large-document behavior must be selected during planning and documented in the UI/README.

### 14.6 Security considerations

- Do not enable arbitrary raw HTML merely to match one preview tool.
- Sanitize any HTML pipeline with a maintained allowlist sanitizer.
- Validate URLs and add external-link isolation attributes.
- Do not request broad filesystem access when a normal file input suffices.
- Avoid remote telemetry that could capture filenames or contents.

## 15. Non-functional requirements

### NFR-001 - Reliability

- No reasonable input should cause an uncaught error or unrecoverable blank screen.
- The previously valid document survives a failed replacement attempt.
- Copy failures do not alter or discard the document.

### NFR-002 - Performance

- The interface should acknowledge a file-selection action within 100 ms.
- For a representative technical document up to 1 MB on a modern laptop, preview should normally become usable within 1 second.
- Scrolling and interaction should remain responsive for representative long documents.
- Expensive optional features should be deferred, lazy-loaded, or omitted if they threaten the core experience.

These are initial product targets, not guarantees for arbitrary file sizes or devices.

### NFR-003 - Compatibility

- Core upload, preview, and plain-text copy should work on current stable Chromium, Firefox, and Safari where their platform APIs permit.
- Rich multi-MIME copy should work on supported secure-context browsers and degrade clearly elsewhere.
- The public deployment must run over HTTPS.

The final supported-version matrix must be recorded during implementation planning and verified before release.

### NFR-004 - Accessibility

- The core workflow targets WCAG 2.1 AA as described in Section 13.
- Automated checks are supplemented by keyboard and screen-reader-oriented manual review.

### NFR-005 - Privacy

- Document contents remain local to the browser session.
- No server-side storage or content analytics are used.
- Removing the file clears app-held references to its content.

### NFR-006 - Maintainability

- Business behavior is not embedded solely in visual components.
- Core transformations have focused tests.
- Dependencies are purposeful and documented.
- README documentation explains setup, design and technical decisions, AI-assistant use, limitations, and future improvements.

### NFR-007 - Visual quality

- All required Markdown elements share a consistent system for typography, color, spacing, borders, and overflow.
- Empty, loading, document, error, drag, copy-success, and copy-failure states are designed—not browser-default accidents.
- No clipped controls, page-level horizontal overflow, illegible code, or broken tables at supported widths.

## 16. Testing and validation requirements

### 16.1 Rendering coverage

Tests must include at least:

- Each required element in isolation.
- Combinations of inline formatting.
- Ordered, unordered, mixed, and nested lists.
- Left/center/right-aligned table columns and wide tables.
- Fenced code with known, unknown, and absent language labels.
- Long lines, URLs, Unicode, and empty elements.
- Malformed/unclosed emphasis, links, tables, lists, and code fences.
- The entire supplied `requirements/open_test_case.md` document.

### 16.2 File workflow coverage

- Picker success and cancellation.
- Drag/drop success and invalid drops.
- Empty file.
- Unreadable or clearly invalid file.
- Successful replacement.
- Failed replacement preserving the existing document.
- Removal and reset.

### 16.3 Clipboard coverage

- Clipboard item includes HTML and plain text in a supporting browser.
- Markdown is included only where supported without breaking other formats.
- Plain-text fallback works when rich writing is unavailable.
- Permission denial is recoverable.
- Export excludes application chrome.
- Manual paste into at least one rich-text editor and one plain-text editor.

### 16.4 Accessibility and responsive coverage

- Keyboard-only complete flow.
- Visible focus and sensible focus restoration.
- Status/error announcements.
- Automated accessibility scan with no serious core-flow violations.
- Mobile, tablet, and desktop viewport review.
- 200% browser zoom review.
- Reduced-motion behavior if animation exists.

## 17. Success criteria

The v1 product is successful when:

1. All explicitly required Markdown elements render correctly in the supplied document and dedicated fixtures.
2. Reasonable malformed Markdown does not crash the application.
3. A user can upload, preview, copy, replace, and remove a document without instruction beyond the interface.
4. A supporting browser writes rich HTML and plain text through one Copy action, with original Markdown added where supported.
5. Pasting into a tested rich-text destination retains useful hierarchy and formatting; pasting into a text-only destination remains readable.
6. The complete core workflow is keyboard accessible and usable on mobile and desktop.
7. No document content is transmitted or persisted outside the current browser session.
8. Required functionality has automated coverage and the representative sample passes manual visual review.
9. The application is deployed publicly over HTTPS and the repository contains the required explanatory documentation.
10. Any known limitations or incomplete items are stated honestly in the README.

## 18. Release deliverables

- Public GitHub repository with complete source.
- Public HTTPS deployment on a suitable static/frontend host.
- Concise README containing:
  - Setup and run instructions.
  - Design decisions.
  - Technical decisions and dependency rationale.
  - Accessibility and testing notes.
  - AI coding assistant usage.
  - Known limitations and incomplete items.
  - Improvements that would be made with more time.
- Submission of repository, deployment, and explanatory text through the form specified in the assignment.

## 19. Risks and mitigations

| Risk | Impact | Product mitigation |
|---|---|---|
| Browser rejects `text/markdown` or multi-MIME clipboard data | Copy appears unreliable | Detect/attempt formats independently and preserve HTML/plain text; fall back to plain text. |
| Copied HTML loses app CSS | Poor paste quality | Build a dedicated self-contained semantic HTML export with portable styling. |
| Raw Markdown includes unsafe HTML or URLs | XSS, navigation, or privacy issue | Keep raw HTML disabled or sanitized; validate schemes; isolate external links. |
| Wide tables/code break mobile layout | Low usability and visual score | Constrain overflow at the element level and test narrow widths. |
| Parser differences appear in hidden tests | Rendering inaccuracies | Use a maintained GFM implementation and create focused fixtures for every required construct. |
| Large documents block the main thread | Frozen interface | Establish a documented size policy, provide progress/feedback, and avoid heavy optional transforms. |
| Optional syntax consumes limited assignment time | Core quality suffers | Gate all enhancements behind completed must-have acceptance criteria. |

## 20. Future scope

Only consider these after v1 success criteria are met:

- Syntax highlighting for common fenced-code languages.
- Math rendering with KaTeX.
- GitHub-style admonitions and definition lists.
- Mermaid diagram rendering with strict security controls.
- A generated table of contents and heading navigation for long documents.
- Theme selection and print-friendly presentation.
- Download as HTML, PDF, or DOCX.
- Optional Markdown editing and split preview.
- Multiple-file navigation and relative local asset handling using explicitly granted files.
- Persisted preferences, recent files, or installable PWA behavior.

## 21. Open questions requiring validation before implementation planning

1. What maximum file size should v1 support, and what exact warning/rejection behavior should apply above it?
2. Should `.txt` files be accepted when users explicitly choose them, or should selection be limited to `.md` and `.markdown`?
3. Should remote images render by default, be blocked for privacy, or require user consent? Images are not explicitly part of the required syntax list.
4. Which browser versions form the formal support matrix?
5. Which rich-text destination will be the required manual acceptance target: Google Docs, Microsoft Word, or both where locally available?
6. After the core passes, which single enhancement offers the best value within the time budget: syntax highlighting, long-document navigation, or another option?

Conservative defaults are defined in the project context until these questions are resolved.
